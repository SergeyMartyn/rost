## Утверждённые правила

- Семья: 10% каждому, без проверки отношений покупателей.
- Приведи друга: 10% пригласившему и новому участнику. Приглашение прежнего участника не подходит.
- Два вида акции, один код на заказ из двух билетов. Семейная основа FAMILY10 утверждена пользователем; в конец добавляется буква источника: FAMILY10T, FAMILY10K, FAMILY10S, FAMILY10M, FAMILY10X. Соответствие подтверждено пользователем: T = Тимур, K = Кристина, S = Сергей, M = Марго, X = Максим. Для приглашения друга при начале реализации принята предложенная основа FRIEND10: FRIEND10T, FRIEND10K, FRIEND10S, FRIEND10M, FRIEND10X.
- Суффикс показывает, кому из команды принадлежит использованный код, а не личность покупателя. Все варианты одного вида акции дают одинаковые 10%, сохраняют одинаковые ограничения и не суммируются.
- VIP guest_peak исключён. Регистрация ведущего, медиапакет и предоплата также не относятся к скидке на билет участника.
- На ТИ обычный билет €80 становится €72. Для Нюрнберга предусмотреть €29 → €26,10, включение не срочное.
- Уточнение пользователя: код действует только на два обычных билета в одном заказе. После применения появляется обязательное имя второго участника. Один контакт покупателя, один платёж за двоих. Без кода один билет; удаление кода очищает второе имя и возвращает один билет. На один заказ применяется один код.

## Что проверено в текущем коде

- TicketPurchaseDialog.astro обслуживает общий сценарий покупки и имеет второй шаг перед выбором Stripe/PayPal. Есть общие Button и ui-field.
- worker/tickets.ts содержит цены и привязку к событиям/вкладкам; worker/orders.ts создаёт Checkout Session и PayPal Order по API. Это не две фиксированные платёжные ссылки.
- Клиентская цена игнорируется. Stripe и PayPal сравниваются с amount_cents конкретного заказа в D1, что позволяет сохранить окончательную сумму со скидкой.
- worker/sheets.ts отправляет подтверждённые оплаты, хранит квитанции выгрузки и повторяет неудачные доставки через cron.
- Apps Script сохраняет первые 9 колонок, следующие 7 используются для ведущих. Дубли отсеиваются по ID заказа.

## Интерфейс и дизайн-система

На шаге оплаты после выбранного билета и перед выбором провайдера разместить раскрываемое действие «Есть промокод?». В раскрытом виде: стандартное поле ui-field, Button secondary/compact «Применить», сообщение результата с aria-live. На телефоне поле может занимать отдельную строку, без уменьшения шрифта и области нажатия.

После серверной проверки показать: два билета 2 × €80 = €160, скидка 10% −€16, к оплате €144. Дать действие «Убрать». Не использовать отдельный экран, новое модальное окно или новый визуальный стиль. Подготовить независимые RU/DE подписи и ошибки. Изменение текста кода делает прежний результат недействительным до нового применения; кнопки провайдера на время проверки заблокированы. VIP получает понятное сообщение о неприменимости, без молчаливого перехода к полной цене.

## Единый расчёт на сервере

Добавить модуль worker/promotions.ts с проверкой применимости и расчётом в целых евроцентах. Для 10% скидка каждого участника округляется в евроцентах; с кодом quantity=2, base_amount_cents=цена одного билета × 2, discount_cents=округлённая скидка одного билета × 2, amount_cents=base_amount_cents-discount_cents. Без кода quantity=1. В Stripe передаются количество 2 и цена одного билета после скидки, в PayPal общая сумма пары. Это правило округления фиксируется тестами, не зависит от способа оплаты и языка браузера.

Новый POST /api/orders/quote принимает билет и код, возвращает базовую цену, скидку и итог, не создавая заказа/оплаты и не требуя имени покупателя. Не возвращает список действующих кодов. Проверки типа билета, активности события, расписания акции и срока раннего тарифа общие с созданием заказа.

POST /api/orders повторно рассчитывает сумму перед сохранением. Клиент передаёт код, билет и ожидаемый результат расчёта только для обнаружения изменения цены; сервер никогда не доверяет этому результату как источнику цены. Если между показом и нажатием цена или акция изменились, вернуть конфликт и новый расчёт для подтверждения, а не списывать другую сумму молча. Ошибочный код нельзя молча проигнорировать.

В Stripe передаются quantity и unit_amount=amount_cents/quantity, в PayPal amount передаётся общая amount_cents нового заказа. Для пары сервер требует второе имя длиной 2-80 символов; клиентское quantity=1 с промокодом отвергается. Промокоды не дублируются в кабинетах провайдеров, повторное применение скидки у провайдера не включается. В webhook проверяется сохранённая итоговая сумма, валюта, аккаунт и платёжная сессия. Изменение или отключение акции впоследствии не меняет цену уже созданной сессии; она действует до собственного истечения. Возврат относится к реально уплаченной сумме.

## Хостинг и данные

Использовать существующие Cloudflare Worker и D1. Отдельные сервер, CMS, KV или новый платёжный сервис не требуются.

Добавочная миграция создаёт promotions: полный код с нормализацией регистра/пробелов, вид акции family/referral, источник issuer_code и подтверждённое имя источника, процент, active, даты начала/окончания при необходимости. Общие правила вида акции переиспользуются всеми суффиксами, чтобы не поддерживать процент и ограничения отдельно для каждого человека. Полный код должен существовать в серверном списке: произвольная добавленная буква не делает код действительным. Отдельная область применимости связывает код с event_id и допустимыми ticket_type: явное разрешение обычного билета и запрет VIP/ведущих. Обычный/ранний тип одного тарифа проверяются по текущему серверному каталогу и сроку продажи. Нюрнберг можно включить независимо, не меняя процент.

Изменение промокодов и активности возможно в D1 без новой сборки сайта. Публичного редактирования нет. В первой версии обслуживаем через существующий административный доступ, без новой админ-панели; изменения делает ответственный оператор или ассистент по указанию пользователя. Таблица Google остаётся отчётом, а не источником цены на каждом checkout.

В orders добавить base_amount_cents, discount_cents (0 по умолчанию), promo_code, promotion_kind, discount_percent, issuer_code и снимок имени источника, версию правила при необходимости. Для новых заказов сохранять полный снимок расчёта и источника, чтобы последующее переименование не меняло историческую атрибуцию. Для исторических заказов без скидки безопасно считать base_amount_cents равным прежнему amount_cents; не менять сумму, статус, продавца или провайдера. Старые схемы должны оставаться совместимыми во время добавочной миграции.

Не хранить названия кодов в публичном JS/HTML как список. Общие коды всё равно можно переслать другому человеку: они дают скидку, а не доказывают право на неё. Для небольшого знакомого сообщества это осознанная ручная модель. Автоматические лимиты на семью/пару и проверка новых участников требуют другого объёма задачи и дополнительных идентификаторов; их не выдавать за реализованную защиту.

## Google Sheets

Оставить первые 16 колонок на своих местах. Дописать справа Q: базовая цена, R: скидка %, S: скидка €, T: промокод, U: акция, V: источник кода, W: количество билетов, X: имя второго участника. Существующая H «Сумма, €» остаётся фактически оплаченной суммой. Пример нового обычного ТИ-билета: H=144, Q=160, R=10, S=16, T=FAMILY10T, U=Семейная, V=Тимур, W=2, X=имя второго участника. Для ведущих новые поля пустые. Источник берётся из серверной записи, а не из свободного текста покупателя.

Строки участников расширять с заполнением пустых J:P, чтобы скидка не попала в колонки ведущих. Обновить Apps Script, заголовки и оба пути отправки: непосредственно после подтверждения и восстановление пропущенных отправок cron. Сохранять числовые значения сумм для суммирования в Sheets, защиту от формул в пользовательских полях и дедупликацию по ID. Уже выгруженные строки и квитанции не пересылать и не дублировать.

Из кода понятно, какая скидка использована и кому из команды принадлежит код. Суффикс не доказывает, кто фактически переслал код, и не связывает пригласившего с новым другом. При необходимости команда отмечает связь вручную в отдельном примечании; новые обязательные персональные поля не добавлять без потребности.

## Проверки и выпуск

1. Локальная тестовая D1 и имитации провайдеров: корректный/неверный/выключенный код, регистр и пробелы, оба кода, запрет VIP/ведущих/архива, округление, сроки, подмена суммы, смена цены после расчёта.
2. Для Stripe и PayPal проверить сумму со скидкой, сохранение снимка заказа, неподходящий webhook, повторное событие, старый заказ без скидки, возврат и ошибку провайдера. Проверить cron и однократную доставку расширенной строки в нужную вкладку.
3. В браузере RU/DE: раскрытие, клавиатура, результат/ошибки, удаление кода, смена тарифа, итог и блокировка оплаты при устаревшем расчёте; телефон и desktop.
4. После отдельного разрешения на публикацию: зафиксировать агрегаты и bookmark production D1, подготовить совместимые колонки и Apps Script, применить добавочную миграцию, выпустить Worker и UI вместе. Проверить public config и live-привязки к Тимуру. Production не переводить в test ради локальных проверок.
5. Не создавать реальное списание без отдельного разрешения. Тесты/создание checkout/статус live и завершённая реальная покупка подтверждают разные этапы.

## Исправление на парный заказ

Миграция 0006_promo_pairs.sql добавляет quantity (по умолчанию 1) и second_participant_name. Существующие покупки и цены не меняются. Выгрузка и cron включают оба поля; один платёж по-прежнему даёт одну строку и один ID заказа. На рабочих листах добавлены и проверены W:X. Исторические строки, уже отправленные до расширения, не переписываются: пустая W в них означает прежний одиночный заказ.

## Состояние реализации

При применении миграции активны все десять кодов для обычных билетов ТИ. VIP и ведущие исключены дополнительно в коде, поэтому случайное добавление области в БД не включает для них скидку. Нюрнберг подготовлен с active=0 в discount_scopes; включается отдельно. Код без суффикса и неизвестные суффиксы не принимаются.

В рабочей таблице Q:V уже подготовлены. Текущий удалённый Apps Script принимает более длинные строки, что было установлено при прежнем расширении для ведущих; повторная публикация скрипта для дополнительных полей не нужна. Локальный образец .gs обновлён до 24 заголовков для следующих установок/изменений. Финальная проверка реальной строки нового оплаченного заказа остаётся отдельной от локальных тестов: фиктивные платежи в production не записывать.

После миграции 0007 для отключения конкретного кода: discount_codes.active=0. Для отключения вида акции: discount_campaigns.active=0. Для включения Нюрнберга: discount_scopes.active=1 только у event_id=nuremberg-2026-12-12. Менять параметры только через закрытый административный доступ, не через общедоступную таблицу. Источники и сумма фиксируются в orders и сохраняются при изменении правил.
