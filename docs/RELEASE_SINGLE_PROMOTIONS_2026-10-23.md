## Поведение

- PROMO10T, PROMO10K, PROMO10S, PROMO10M, PROMO10X: один обычный ТИ-билет, 10%, €80 → €72.
- Суффиксы: Тимур, Кристина, Сергей, Марго, Максим соответственно.
- FAMILY10 и FRIEND10 с прежними суффиксами: два обычных билета, 10% каждому, €160 → €144, обязательное второе имя.
- Переключение на одиночную акцию очищает и отключает второе имя. При возврате к парной акции его требуется ввести заново.
- Количество и цена определяются правилом в D1, не префиксом на клиенте. Клиентское количество проверяется сервером; сумма клиента не используется.
- VIP, ведущие и архив исключены. Нюрнберг остаётся отключён для всех трёх акций.
- Google Sheets использует существующие Q:X; для одиночной акции U=Одиночная скидка, W=1, X пустая. Прежние квитанции выгрузки и дедупликация сохраняются.

## Использованный порядок публикации

1. Следовать `RELEASE_CHECK_2026-10-20.md`: прочитать актуальные настройки Worker, подтвердить прежнюю production D1, live и аккаунты Тимура, сохранить агрегаты и bookmark.
2. Применить только отсутствующие миграции по журналу D1, включая `0007_single_promotions.sql`. Она создаёт новые таблицы конфигурации и копирует прежние правила, коды и области действия; заказы не переписывает. Не повторять уже применённые миграции и не запускать очистку/seed.
3. Выпустить новый Worker и UI вместе. До его выпуска старый Worker не читает новые таблицы и отвергает PROMO-коды; прежние пары продолжают работать. Не добавлять PROMO-коды в старую promotion_codes.
4. Повторить проверки live-конфигурации, агрегатов, всех видов quote и интерфейса RU/DE без реального списания. Для новой конфигурации использовать discount_campaigns/discount_codes/discount_scopes; promotion_* после миграции остаются только снимком для отката.
5. После проверки вернуть локальный генерируемый конфиг в test. Реальная покупка и строка такого платежа в рабочей таблице требуют отдельной фактической оплаты; имитации провайдеров этого не подтверждают.

Откат: предыдущий Worker продолжает читать сохранённые promotion_*; PROMO станет недоступен, а созданные до отката заказы сохранят сумму и количество, по которым обрабатываются webhook/capture. Более поздние изменения discount_* автоматически в прежние таблицы не переносятся.
