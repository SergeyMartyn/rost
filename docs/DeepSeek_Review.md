## 1. Что это за проект

R.O.S.T. — русскоязычное сообщество в Германии. Публичный смысл — живое общение, знакомства, «люди, с которыми захочется встретиться снова»; встречи, игры и другие форматы служат этому. Двуязычный (RU/DE) статический сайт-визитка сообщества с анонсами двух пилотных событий (Регенсбург, Мюнхен), формой интереса к билету (без оплаты), страницами «О нас», «Контакты», Impressum, Datenschutz, «Условия участия» и баннером согласия на cookie.

**Стек:** Astro 7 (static output), TypeScript 6, Tailwind CSS v4 через `@tailwindcss/vite`, vanilla-cookieconsent v3, деплой на Cloudflare Workers Static Assets (Wrangler 4). Единственная серверная логика — выбор языка на `/` в `worker/index.ts`. Контент и маршруты описаны в `site.config.json`; тексты RU/DE лежат прямо в компонентах.

**Архитектура и проверки (сильные стороны):**
- Статическая генерация: HTML без зависимости от рантайма, 14 страниц (`getStaticPaths` в `src/pages/[...path].astro:19`).
- Один источник маршрутов `site.config.json` → `src/lib/site.ts:6`; оттуда же ссылки, переключатель языка, canonical, hreflang, sitemap.
- Хорошая культура тестов: unit (`tests/language.test.ts`) + браузерные (`tests/browser/*.spec.ts`), включая проверку «нет внешних запросов до согласия» и адаптив без горизонтального скролла.
- Приватность выстроена грамотно: Consent Mode Basic, click-to-load фасады, `youtube-nocookie`, самохостинг шрифтов.

## 3. Качество кода и архитектура

**Сильное:**
- Строгий TS (`tsconfig.json` → `astro/tsconfigs/strict`), `astro check` без ошибок.
- Типы `Language`/`Page` выводятся из конфига (`src/lib/site.ts:2-3`) — маршруты нечаянно не «потерять».
- Разделение lib/компоненты/layout/worker логичное; фасады и consent вынесены в `src/lib/`.
- Комментарии в `consent.ts`/`services.ts` реально объясняют «почему» (со ссылками на пункты требований) — редкая и полезная практика.

**Проблемы:**
1. **Нет единого источника данных о событиях.** Даты, цены и адреса продублированы минимум в четырёх местах: `src/components/Events.astro:14-57`, `src/components/EventPage.astro:7-132` и `:574-584`, `src/components/Faq.astro:40-43,93-96`, `src/components/ParticipationTerms.astro:14,35`. Документация уже фиксировала расхождение 29/30 € (`PROJECT_CONTEXT_v2.md:72`). Браузерные тесты (`tests/browser/events.spec.ts:261`) частично ловят рассинхрон, но это «заплатка», а не защита. Рекомендация: вынести события в `src/data/events.ts` (или секцию `events` в `site.config.json`) и рендерить всё оттуда.
2. **`src/components/EventPage.astro` — 790 строк** с большим инлайн-скриптом форм и валидацией (~250 строк JS). Компонент перегружен; логику формы стоит вынести в отдельный модуль/скрипт и типизировать данные билетов.
3. **Хрупкий сентинел для видео:** `media.ts:8-13` использует `'xxxxxxxxxxx'` как «нет видео», а `VideoFacade.astro:21` сравнивает по строке. Лучше `videoId?: string | null` и `undefined`/`null`.
4. **Хрупкая эвристика заголовков в правовых текстах:** `src/pages/[...path].astro:80-95` определяет заголовок абзаца по длине строки `< 120`. Работает, но сломается на длинном заголовке. Надёжнее — структурировать тексты (массив секций в конфиге).
5. **Мёртвые строки:** поле `intro` в `src/lib/site.ts:23,46` — наследие шаблона, нигде не используется.
6. **Незакоммиченные файлы, от которых зависит сборка (важно!).** `git status` показывает untracked `src/components/ParticipationTerms.astro`, `public/images/` и `design/`, при этом `src/pages/[...path].astro` уже импортирует `ParticipationTerms`. При клоне репозитория без этих файлов **сборка упадёт**. См. P0 в §9.

**Мелкое, но стоит поправить:**
- Социальные иконки — «мёртвые» `<span>` (`src/components/Header.astro:141-147`), у картинок есть `alt` (`Instagram`/`YouTube`/`Telegram`), но нет ссылки и нет `aria-hidden`. Скринридер объявляет ссылки, которых нет. Либо обернуть в `<a>` с реальным URL, либо пометить `aria-hidden="true"` до появления профилей.
- `aria-label="Social Media"` в `Header.astro:141` не локализован (единственная жёсткая английская строка среди RU/DE-копий).

## 4. Скорость и производительность

**Сильное:**
- Полностью статический HTML с CDN Cloudflare; нет SSR-задержек.
- Заголовок LCP — текст (hero), не картинка; изображения карточек `loading="lazy" decoding="async"` (`src/components/Events.astro:112-113`).
- Внешние ресурсы не подключаются до согласия и до клика — нет `preconnect`, `dns-prefetch`, сторонних шрифтов (`tests/browser/consent.spec.ts:34`, README:52). Это одновременно и скорость, и приватность.
- Шрифты самохостинговые, `font-display: swap` (`src/styles/global.css:8-38`), суммарно ~160 КБ woff2.

**Проблемы:**
1. **Полноразмерные фото в лайтбоксе.** `public/images/rost-networking.png` — **4,24 МБ**, `public/images/rost-ti.jpg` — **4,82 МБ**; они подставляются как `data-photo-full` (`Events.astro:97`, `:60-71`) и грузятся целиком по клику. Это самый тяжёлый ресурс сайта. Нужно: пережать (WebP/AVIF), ограничить по длинной стороне (напр. 1920–2560 px), а карточкам отдавать отдельный уменьшенный размер. Превью (`-preview.webp`, 100–147 КБ, 1200 px) в целом разумны, но и они без `srcset`/`sizes` — на мобильном грузится 1200 px под карточку шириной ~350 px.
2. **Вес JS/CSS на каждой странице.** В `dist/_astro`: `Consent...js` — **61,9 КБ** (это библиотека vanilla-cookieconsent), `global.css` — 49,7 КБ, `Consent.css` — 36,7 КБ. Баннер подключён через `<script>` в `src/components/Consent.astro` на всех страницах и тянет библиотеку целиком, даже несмотря на ранний выход `initConsent()` при пустом списке сервисов (`consent.ts:134`) — импорт и CSS всё равно загружаются. Для сайта-визитки 62 КБ стороннего JS ради cookie-баннера многоразово. Варианты: подключать `vanilla-cookieconsent` динамическим `import()` и/или вынести баннер в отдельный лениво загружаемый чанк.
3. **Нет `preload` для критического шрифта.** Первый экран набран `Marmelad` (`--font-display`, `global.css:65`); без `<link rel="preload">` возможен FOUT/скачок. Добавить preload для `Marmelad-Regular.woff2` (и, возможно, `Onest-Regular`).
4. **Кэширование отдаёт CDN.** Явного `_headers`/Cache-Control нет — полагаемся на дефолты Cloudflare (HTML ревалидируется, `_astro/*` хешируется). Стоит зафиксировать `Cache-Control: public, max-age=31536000, immutable` для `/_astro/*` и разумный TTL для `public/`-ассетов через `public/_headers` (см. §5).
5. `width`/`height` превью заданы 1920×1080 и 3840×2555, тогда как реальный файл 1200×675/1200×798 (`Events.astro:60-70`). Резерв пропорций работает по отношению, но значения вводят в заблуждение и рассинхронизируются с ассетом.

## 5. Безопасность и приватность

**Сильное (это действительно хорошо сделано):**
- **Ничего не грузится до согласия.** `consent.ts:63-86` сначала кладёт `consent default` (всё `denied`, кроме `security_storage`) в `dataLayer`, только потом подключает GTM; проверяется тестом `tests/browser/consent.spec.ts:95-133`.
- **Click-to-load фасады** для YouTube и Google Maps: до клика ни iframe, ни запроса (`src/lib/facade.ts`, `src/components/VideoFacade.astro`, `MapFacade.astro`). YouTube через `youtube-nocookie.com` (`media.ts:18-19`).
- **Нет XSS-поверхности в форме.** Данные билета не отправляются и не сохраняются, вывод через `textContent` (`EventPage.astro:774-775`), без `innerHTML`; `preventDefault` стоит (`:752-753`).
- Cookie `site_language` — `SameSite=Lax`, `Secure` на https (`Layout.astro:113`).
- Referrer для iframe — `strict-origin-when-cross-origin` (`facade.ts:19`).
- Секреты Cloudflare не в репозитории; `.gitignore` закрывает `.env*`, `.dev.vars*`, `wrangler.generated.json`.

**Проблемы / риски:**
1. **Нет security-заголовков.** Ни `public/_headers`, ни блока в `worker/index.ts`: отсутствуют `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, `Strict-Transport-Security`. Cloudflare добавляет часть по умолчанию (HSTS — только если включён в дашборде), но CSP и запрет MIME-sniffing надо задать самим. Для статики CSP реалистичен и рекомендуется: `default-src 'self'` + явные `frame-src`/`script-src` для GTM и фасадов. **Это P0 перед публикацией.**
2. **Правовой текст расходится с реализацией.** В `site.config.json` раздел Datenschutz «b) Bei Nutzung unseres Kontaktformulars oder der Anmeldung zu Treffen» описывает сбор имени, e-mail и телефона при регистрации/через контактную форму, но регистрация и оплата не подключены (`PROJECT_CONTEXT_v2.md:63`). Также есть раздел о фото/видеосъёмке, тогда как видео — заглушка. Формулировки не выдумывать, но перед публикацией владельцу/юристу нужно согласовать текст с фактической функциональностью (или наоборот).
3. **Impressum/оператор.** Ответственное лицо указано через `c/o IP-Management #8852, Ludwig-Erhard-Str. 18, Hamburg` (`site.config.json:7-8`). Для сайта, который в перспективе продаёт билеты, стоит отдельно проверить юридическую достаточность и «доступность» адреса. Это вне кода, но важно для доверия и GDPR.
4. **Зависимости.** `npm audit`: 3 moderate (прямой `wrangler`, транзитивные `miniflare`/`undici`). Это **dev-инструменты**, в рантайм сайта не попадают — риск низкий, но `wrangler` стоит обновить при удобном случае.
5. **Косметика:** `deleteCookieEverywhere` (`consent.ts:90-99`) мутирует массив во время итерации по его копии — работает, но читается как потенциальный баг; лучше собрать список доменов заранее.
6. `esc()` в `consent-texts.ts:11-12` не экранирует кавычки; в атрибут `href` попадает `policyUrl` без экранирования (`:45`). Данные заданы разработчиком, эксплуатации нет, но при добавлении сервисов из внешнего источника это станет дырой. Мелочь на будущее.

## 6. SEO

**Сильное:**
- Корректные canonical и `hreflang` (de/ru/x-default) на всех страницах (`Layout.astro:31-43`), проверяется тестом `tests/browser/site.spec.ts:12-19`.
- `sitemap.xml` с alternates (`src/pages/sitemap.xml.ts`), `robots.txt` со ссылкой на sitemap (`robots.txt.ts`).
- `/` — `noindex,follow` + 302 от Worker (`index.astro:11`, `worker/index.ts:47-54`), локализованные пути не редиректятся.
- Уникальные локализуемые URL с транслитерацией для RU (`/ru/meropriyatiya/` и т. п.).
- Семантическая разметка: один `h1` на страницу, `section aria-labelledby`, `time[datetime]` для дат (`Events.astro:125`), осмысленные alt/aria у изображений и кнопок.

**Проблемы:**
1. **Пустые meta description на всех страницах, кроме главной.** `[...path].astro:38-40` формирует `{page} — R.O.S.T.`, в сборке это буквально `"Veranstaltungen — R.O.S.T."`, `"Kontakt — R.O.S.T."`, `"Impressum — R.O.S.T."`, `"Über uns — R.O.S.T."` (видно в `dist/**/index.html`). Для коммерчески значимых страниц (события, о нас, контакты) нужны живые уникальные описания по 120–155 символов на каждом языке. **Это P0.**
2. **Нет структурированных данных (JSON-LD) вообще.** Поиск по `src/` и `dist/` не находит `application/ld+json`. Отсутствуют `Organization`, `Event` + `Offer`, `FAQPage`, `BreadcrumbList`. Для сайта с событиями и FAQ это самый крупный неиспользованный рычаг и для Google rich results, и для AI-ответов. **P1.**
3. **OG/Twitter минимальны и не различаются по страницам.** `og:image` всегда один `social.png` (`Layout.astro:49`); нет `og:site_name`, `og:image:width/height/alt`, `twitter:title/description`. Для шаринга и соцсетей — см. §7.
4. **Заголовки `<title>` брендоцентричны.** «Gemeinsam wachsen · R.O.S.T.» / «Сообщество людей · R.O.S.T.» — без ключевых сущностей («встречи», «Мюнхен», «русскоязычные в Германии»). Полезно расширить, сохранив бренд.
5. **Нет отдельных URL у событий.** Оба события живут якорями на одной странице (`Events.astro` → `/events#regensburg|#games`). Это ограничивает длинный хвост запросов и мешает `Event`-схеме с отдельным `url`. В документации отдельные страницы заявлены как будущая работа (`Structure_v1.md:76`).
6. **Sitemap без `lastmod`** — не критично, но полезно при частых обновлениях.
7. Юридические страницы индексируются (нет `noindex`). Обычно допустимо; решить осознанно.

## 7. SMO (шаринг и социальные сети)

1. **Профили соцсетей нигде не подключены.** В мобильном меню иконки Instagram/YouTube/Telegram — это `<span>` без ссылок (`Header.astro:141-147`). Для community-проекта, чей рост держится на приглашениях, это прямая потеря канала привлечения. Как только владелец даст реальные адреса — обернуть в `<a>` и вынести в конфиг.
2. **Open Graph/Twitter карточки слабые:** один и тот же `social.png` 1200×630 (размер корректный) на всех страницах, без `og:site_name`, `og:image:alt`, `og:type` для событий (можно `website`/`article`). Для событий стоит давать картинку события.
3. Нет кнопок «поделиться» и нет ссылок на сообщество в контенте (кроме мобильного меню без ссылок).
4. После появления профилей добавить их в JSON-LD `Organization.sameAs` (см. §8) — это свяжет бренд с соцсетями и для Google, и для AI.

## 8. AI-оптимизация (GEO/AEO)

1. **Нет JSON-LD** — главный пробел. Минимальный набор: `Organization` (name, url, logo, email, `sameAs`, `knowsLanguage` de/ru) на главной; `Event` + `offers` для встречи и игр (дата, место, цена, валюта, доступность); `FAQPage` для блока FAQ (`Faq.astro` — 8–9 пар «вопрос/ответ» в DOM, идеальный кандидат); `BreadcrumbList` для внутренних страниц.
2. **Контент для LLM уже хорош:** осмысленный семантический HTML, ответы FAQ лежат в DOM (не прячутся за JS), чётко определена сущность бренда и расшифровка R.O.S.T., двуязычие с hreflang. Это сильный фундамент — не хватает только машиночитаемой разметки.
3. **robots.txt не задаёт политику для AI-краулеров.** Сейчас `User-agent: * Allow: /`. Нужно осознанное решение владельца: разрешать (`GPTBot`, `Google-Extended`, `ClaudeBot`, `PerplexityBot`, `CCBot` и т. д.) или ограничивать. Для community, которому нужна видимость, обычно выгодно разрешать явно.
4. **Нет `llms.txt`.** Для AI-ассистентов полезно отдать `/llms.txt` с кратким описанием сообщества, списком страниц, событий и контактов. Дёшево и повышает шанс корректного цитирования.
5. `meta name="keywords"` отсутствует — и это правильно, современные движки его игнорируют.
