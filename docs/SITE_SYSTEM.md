## 1. Задача и принцип

Новое мероприятие должно добавляться как запись с данными и содержимым. Карточку, страницу, навигацию и архив оформляют существующие шаблоны. Редактор выбирает предусмотренный формат события, заполняет поля и подключает доступные блоки; размеры, цвета, кнопки и выравнивание не придумываются заново.

Цепочка: **токены → компоненты → блоки → шаблоны → данные мероприятия**.

Для примерно одного события в месяц предлагается начать с файлового контента Astro Content Collections с проверкой схемы. Это даст единые поля и шаблоны без отдельной административной панели. Если позже понадобится редактор в браузере, CMS подключается к той же модели данных. Tailwind отвечает за стили внутри компонентов, но сам по себе не обеспечивает единообразие страниц.

### Конкретные расхождения

1. `ArchiveIndex.astro`: H1 и вступление не получают адаптивного центрирования. В Penpot, страница `Archiv`, Hero title: desktop — left, tablet/mobile — center.
2. `hero.css`: до 64rem общий Hero центрируется, но `hero--host`, eyebrow и некоторые абзацы имеют отдельные правила выравнивания. Исключения должны стать осознанными вариантами, а не накапливаться по страницам.
3. `TiGamesPage.astro`: H1 использует собственный `clamp(2.25rem,5vw,3.5rem)`; архив — `clamp(2.8rem,6vw,4.5rem)`; основной Hero — другие размеры. Единой шкалы ролей пока нет.
4. `hero__cta`, `site-header__cta` и кнопки с длинными Tailwind-строками в архиве имеют самостоятельные настройки. Внешне похожие элементы не используют единый API.
5. Базовый `--font-sans` — Arial, `--font-hero-sans` — Onest. Часть страниц явно включает Onest. Унификацию основного шрифта нужно провести как отдельное проверяемое изменение.

Это аудит исходников и свойств макетов, а не утверждение о полном визуальном совпадении или всех дефектах сайта.

Цвета отдельных секций уже есть в `global.css`; они остаются палитрой разрешённых поверхностей. Новый цвет сначала получает роль и токен, затем используется в компонентах.

Порог tablet — 48rem, desktop — 64rem. Макеты 390/768/1440 — контрольные размеры, а не три единственные допустимые ширины. Существующее изменение композиции на 80rem в `events.css` нужно отдельно проверить при миграции.

## 5. Выравнивание

**Центрирование контейнера, центрирование текста и ширина кнопки — разные свойства.**

| Элемент | Mobile / tablet | Desktop |
| --- | --- | --- |
| H1, eyebrow, короткое вступление | По центру | Слева у split; по центру у centered |
| Основной CTA первого экрана | По центру в группе действий | По композиции PageIntro |
| H2 самостоятельной вводной секции | По центру | По варианту SectionHeading |
| Длинный текст, программа, FAQ, поля форм | Слева | Слева |
| Заголовок и текст карточки | Слева | Слева |
| Хлебные крошки | Слева | Слева |

PageIntro имеет ограниченный набор вариантов: `split` (текст + медиа/панель на desktop), `centered` (вводный блок по центру), `legal` (узкая текстовая колонка). Все варианты центрируют H1 на mobile/tablet. Длинное вступление разделяется на короткий lead и обычный текст ниже.

Для игр desktop-панель билетов может оставаться справа, а mobile-форма и поля остаются слева при центрированном заголовке. Исключение задаётся внутри функционального блока, а не отменой правил всей страницы.

Запрещено исправлять это общим `h1, h2 { text-align: center }`: такое правило затронет неподходящие контексты. Выравниванием владеют PageIntro, SectionHeading и Actions.

## 6. Кнопки и ссылки

Предлагается один визуальный компонент Button с вариантами; он выводит `<a>` для перехода и `<button>` для действия. Разметка и обработчики конкретных форм остаются в функциональных компонентах.

| Вариант | Вид | Где используется |
| --- | --- | --- |
| primary | Зелёный фон, белый текст | Основное действие: участие, регистрация |
| secondary | Прозрачный фон, зелёная рамка и текст | Дополнительное действие на светлом фоне |
| inverse | Белый фон, зелёный текст | Действие в зелёной секции или Header |
| text | Текстовая ссылка с понятным hover/focus | Навигация и малозначимые переходы |

Размеры: standard — минимум 52px на mobile, 56px от tablet, текст 17px/600, padding по горизонтали 24px и по вертикали 12px; compact — минимум 48px, текст 15px/700, для Header. Иконка при наличии 20px, интервал 8px. Высота не фиксированная: перенос текста увеличивает кнопку.

Основная CTA на mobile: ширина `min(100%, 350px)`, центрирование в контейнере действий. На tablet/desktop — по содержимому. Для нескольких действий mobile использует вертикальный стек с интервалом 12px. Форма может иметь кнопку на ширину своей колонки. Размеры не переопределяются на уровне страницы.

Одна основная цель на группу действий. Повторить регистрацию в конце длинной страницы допустимо; это та же цель и те же данные. Cookie banner и кнопки провайдеров сохраняют свои специальные требования и не заменяются автоматически общими вариантами.

Обязательны состояния default, hover, focus-visible, disabled и loading. Focus видим на выбранном фоне; loading сохраняет подпись/ширину и блокирует повторную отправку; disabled не обозначается одним цветом. Ссылку нельзя «отключить» одним `aria-disabled`, оставив рабочий переход. Иконка без текста получает доступное название. Цветовые пары проходят проверку контраста до утверждения; текущая палитра сама по себе не доказывает доступность.

## 7. Хлебные крошки

Расположение: под Header, внутри общей верхней зоны страницы, над eyebrow/H1; в том же контейнере. На главной и служебном выборе языка крошек нет. Вертикальный интервал до вводного блока — предлагаемые 24px mobile и 32px от tablet.

Иерархии:

- Главная → Мероприятия.
- Главная → Мероприятия → Название события.
- Главная → Прошедшие мероприятия.
- Главная → Прошедшие мероприятия → Название прошедшего события.
- Главная → О нас / Контакты / Ведущим / название правовой страницы.

Компонент Breadcrumbs получает массив `{ label, href? }` из маршрутов и данных страницы. Последний элемент — текст с `aria-current="page"`; остальные — ссылки. Семантика: `nav` с локализованным названием и `ol`, разделители декоративные. На mobile элементы переносятся; длинное название не создаёт горизонтальный скролл. Текст 14px, строки 1.5; интерактивная область ссылок увеличивается padding. RU/DE не смешиваются.

Это новый стандарт навигации, а не описание существующей реализации.

Карточки upcoming/past — варианты EventCard, а не независимые копии. Обложка списка предлагается 4:3, object-fit cover с фокусной точкой; подробная галерея сохраняет композицию оригинала. Нет обложки — применяется единый предусмотренный fallback; нет галереи — блок отсутствует. Счётчики и месяцы архива вычисляются по данным.

Разрешённые содержательные блоки события: описание, для кого, программа, ведущие, место, FAQ, галерея, видео. Порядок и обязательные зоны определяет шаблон. Новому событию не разрешается передавать произвольные CSS-классы для изменения дизайна базовых блоков. Уникальный блок добавляется в библиотеку с описанными вариантами и проверками.

## 9. Модель мероприятия

Одна сущность события объединяет языки; даты, состояние и идентификатор не копируются отдельно для RU/DE.

| Поля | Назначение / проверка |
| --- | --- |
| `eventId` | Неизменный уникальный ID конкретного события; согласован с билетным каталогом |
| `format` | Например meetup / games; выбирает набор разрешённых блоков |
| `publication` | draft / published; draft не попадает в публичные списки и sitemap |
| `startsAt`, `endsAt`, `timezone` | Подтверждённые дата/время и Europe/Berlin; конец не раньше начала |
| `dateOnly` при неизвестном времени | Локальная дата без выдуманного времени; несовместима с точным startsAt |
| `status` | scheduled / past / cancelled; sold-out относится к продаже, а не к факту проведения |
| `location` | Город, подтверждённый адрес или признак «сообщим позже» |
| `locales.ru`, `locales.de` | Название, lead, описание, программа, FAQ, SEO, alt |
| `paths.ru`, `paths.de` | Постоянные публичные URL; уникальны и связывают переводы |
| `cover`, `gallery`, `video` | Локальные/подтверждённые медиа, размеры и подписи |
| `ticketKeys` | Ссылки на серверный каталог билетов; необязательны для бесплатного события |
| `recap` | Материалы после встречи; отсутствие recap не препятствует закрытию регистрации |

Окончательные имена/типы закрепляются при реализации схемы. Это контракт данных, не готовая TypeScript-схема. Проверка публикации требует обе локали, корректные даты/пути и обязательные поля; необязательные блоки могут отсутствовать.

Цены и доступность продажи определяются серверным билетным каталогом. Отображение стоимости получает данные из согласованного источника; нельзя вручную размножать суммы по переводам. Если витрина строится статически, цены проверяются при сборке, а текущая доступность/сумма повторно проверяются сервером при покупке. Исторические eventId, ticket keys и заказы сохраняются. Дизайн-система не меняет существующие правила платежей.

### Постоянный URL и архив

Для новых событий URL должен обозначать конкретную встречу (например, содержать год/дату), а не только формат. После завершения тот же URL открывает страницу в режиме past; событие попадает в список архива. Перенос физического файла или смена адреса для этого не нужны.

Существующие адреса, включая `tiGames` и `archiveRegensburg`, сохраняются при первой миграции. До повторного использования адреса игр нужно отдельно решить: это постоянная страница формата или адрес конкретного выпуска. Если понадобится новый адрес, составляется карта перенаправлений и проверяются прежние рекламные ссылки/якоря. Тихо подменять прошедшее событие новым нельзя.

### Время и статическая сборка

Списки upcoming/past фильтруются и сортируются при сборке: ближайшие — по возрастанию даты, прошедшие — по убыванию. Клиентский календарь не является источником серверной доступности билета.

Статический сайт сам не обновится в полночь. Для текущего масштаба предлагается редакционный перенос после мероприятия с новой сборкой/публикацией по `EVENTS_LIFECYCLE.md`. Сервер отдельно закрывает продажи к установленному cutoff независимо от свежести HTML. Автоматическую пересборку по расписанию можно внедрить позднее отдельной задачей; сейчас она не настроена этим документом.

Для события с известной только датой cutoff продажи задаётся отдельно после подтверждения организатором. Нельзя выдумывать время окончания, автоматически относить отменённое событие к состоявшимся или считать отсутствие фото признаком будущего события.

## 10. Ежемесячное обновление

1. Создать запись события из образца; дать новый eventId и постоянные RU/DE URL.
2. Заполнить факты, переводы и предусмотренные блоки. Неподтверждённые данные обозначить явно.
3. Для платного события настроить серверные билеты и cutoff; сверить отображаемые цены и условия участия.
4. Проверить карточку на главной, каталог, страницу события, переключение языка и крошки. Черновики не публикуются.
5. Выполнить проверки и визуальное сравнение на двух языках; публикация выполняется отдельным релизом.
6. После проведения закрыть новые продажи, переключить режим, добавить доступные материалы и пересобрать. Проверить архив, старые ссылки и отсутствие предложения купить прошедшее событие.

При отсутствии ближайших встреч показывается единый пустой блок с переходом к архиву/контактам; не оставляются старые даты или вымышленные анонсы. Для отмены показывается отдельный статус с подтверждённой информацией организаторов.

## 11. Как документация становится работающим правилом

Источник реализованных токенов — `src/styles/global.css`; компоненты используют эти токены. Данный документ описывает назначение, варианты и правила применения. Penpot показывает эталонные композиции. При изменении правила документ, код и соответствующие эталоны обновляются в одной задаче с явным статусом проверки.

Нельзя поддерживать три независимо редактируемые таблицы чисел. На первом этапе не вводим ещё один JSON токенов: это потребовало бы генератора и дополнительной синхронизации. Возможный будущий экспорт в Penpot рассматривается отдельно.

Предлагается локальная страница каталога UI: кнопки со всеми состояниями, H1/H2, крошки, EventCard, форма, пустой каталог, past/cancelled. Каталог использует реальные компоненты сайта. Он нужен для визуальной приёмки и не должен попадать в публичный sitemap или релизные HTML-страницы без отдельного решения.

Правила для последующих задач разработки:

- Сначала подобрать существующий компонент и шаблон. Новая запись события не должна требовать новых стилей.
- Стили внутри UI-компонентов могут использовать Tailwind; страницы не копируют их длинные наборы классов.
- Динамические варианты Tailwind задаются таблицей полных классов, а не сборкой `bg-${color}`.
- Изменение общего компонента проверяется на всех его типах страниц, а не только на той, ради которой оно сделано.
- Исключение документируется по назначению компонента и ширине, без правил «для страницы X сдвинуть на 17px».

## 12. Внедрение по этапам

1. **Визуальный пилот.** В отдельном локальном просмотре собрать H1, lead, кнопки, крошки, карточки. Проверить длинные RU/DE названия и согласовать предложенную шкалу/выравнивание. Затем зафиксировать стандарт.
2. **Общие элементы.** Реализовать Button, Actions, Breadcrumbs, PageIntro, SectionHeading. Перенести архив и одну актуальную страницу как образцы; сохранить существующую функциональность.
3. **Шаблоны.** Применить систему к главной, каталогу, остальным внутренним и правовым страницам. Удалить заменённые дубли, проверить Header и мобильное меню.
4. **Контент.** Ввести collection/schema и перенести имеющиеся события без потери переводов, ID и ссылок. Подключить общие выборки к главной, каталогу и архиву.
5. **Защита от расхождений.** Включить проверку схемы/ссылок, значимые браузерные проверки и эталонные снимки после принятия дизайна. Закрепить порядок в документации разработки.

Каждый этап — отдельное проверяемое изменение. Документ не является поручением на немедленный глобальный рефакторинг, commit, push или deploy.

## 13. Приёмка

- Проверить RU/DE на 320, 390, 768, 1024, 1440px и промежуточных 767/769, 1023/1025px; нет горизонтального скролла и обрезанных немецких названий.
- Один H1, последовательные H2/H3; одинаковые роли используют одну шкалу. На mobile/tablet H1 и основной CTA центрируются по установленному правилу.
- Крошки находятся в одной зоне, отражают актуальный режим события и ведут на правильный язык.
- Кнопки сохраняют размер/вариант, допускают длинный текст; клавиатурный focus видим. Диалоги и меню проверяются с клавиатуры, при 200% увеличении и уменьшенной анимации.
- Схема отклоняет дубли ID/URL, неправильные даты, отсутствие обязательного перевода и неизвестные ключи билетов.
- Новое событие добавляется данными, без редактирования CSS и ручного добавления карточек в несколько страниц.
- Прошедшее событие исчезает из ближайших, появляется в архиве по тому же URL; сервер отклоняет новую покупку, исторические заказы доступны существующему платёжному процессу.
- Метаданные, canonical, hreflang и sitemap соответствуют опубликованным записям и постоянным URL.

Для изменений кода: `npm.cmd run check`, `npm.cmd run build`, применимые существующие unit/browser tests. Снимки проверяются глазами; успешная сборка не доказывает визуальное соответствие. Для изменения только этого документа сборка не требуется.
